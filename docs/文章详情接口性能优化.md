# 文章详情接口性能优化

> **一句话**：定位到「读接口按写接口实现」的设计缺陷，通过浏览量异步化 + 多级缓存改造，
> 将文章详情接口 QPS 从 **264 提升到 5730（约 21 倍）**，P95 延迟从 **343ms 降到 17ms**，
> 并让 MySQL 从瓶颈变为近乎空闲。

---

## 一、问题定位

### 1.1 表象

文章详情接口 `GET /api/articles/{id}` 压测时，QPS 从并发 20 起就不再增长，
之后增加并发量只推高延迟。

### 1.2 根因

阅读源码后发现，这个「读」接口实际按「写」接口实现：

```java
@Transactional                              // 开事务
@CachePut(value = "article", key = "#id")   // 请求结束写 Redis
public ArticleVO getDetail(Long id) {
    Article article = getById(id);                                    // SELECT ①
    // ... 权限校验 ...
    lambdaUpdate().setSql("view_count = view_count + 1")...update();  // UPDATE ② 行锁
    ArticleVO vo = baseMapper.selectDetailWithAuthor(id);             // SELECT ③ JOIN
    return vo;
}
```

**每个请求 = 1 个事务内的 2 次 SELECT + 1 次 UPDATE + 1 次 Redis 写入。**

其中 UPDATE 带来两个代价：

1. **行锁竞争**——所有访问同一篇文章的请求在同一行上排队
2. **redo 刷盘**——MySQL 默认 `innodb_flush_log_at_trx_commit=1`，
   每次事务提交都要 fsync redo log

### 1.3 用对照实验分离因子

| 实验条件 | 并发 20 | 并发 80 | 结论 |
| --- | --- | --- | --- |
| 4 篇文章（高度集中） | 141 QPS | 140 QPS | 行锁严重 |
| 200 篇文章（分散） | 421 QPS | 975 QPS | **行锁贡献约 3–7 倍** |
| 200 篇 + `flush=2` | 943 QPS | 1599 QPS | **刷盘贡献约 2 倍** |

两个因子**根因相同**：都是那个同步 UPDATE。

### 1.4 一个被证伪的假设

HikariCP 默认连接池是 10，而并发 10 就出现饱和——这个巧合很容易让人误判。
实测把池扩到 50：

| 并发 | 池=10 | 池=50 |
| --- | --- | --- |
| 20 | 141.3 | 137.0 |
| 80 | 139.7 | 131.8 |

**毫无变化**。避免了一次无效优化。

## 二、优化方案

### 2.1 浏览量异步化（治本）

| | 改造前 | 改造后 |
| --- | --- | --- |
| 计数写入 | 每次请求同步 `UPDATE` | Redis `INCR`，不碰数据库 |
| 落盘 | 即时 | 定时任务每 5 分钟批量回写 |
| 显示值来源 | 数据库 | Redis |
| 事务 | 每请求一个写事务 | 无（详情页不再写库） |

关键实现细节：

- **用 `SETNX` 初始化基线**：并发下若用「GET 判空再 SET」，两个线程可能同时读到空、
  各自写一次基线，后写的会覆盖先写的导致计数归零
- **回写用绝对值覆盖而非累加**：`SET view_count = ?`。
  若用 `view_count = view_count + N`，回写任务重复执行会造成重复计数
- **SCAN 而非 KEYS**：`KEYS` 一次性遍历会阻塞 Redis 单线程，key 一多就拖垮实例
- **`@PreDestroy` 停机回写**：避免最后几分钟的计数随进程退出丢失

### 2.2 缓存层重构

- **`@Cacheable` 必须放独立 Bean**：Spring 缓存注解依赖 AOP 代理，
  **类内自调用会让注解静默失效**（不报错，就是不生效）。
  原 `getDetail` 若直接调用本类的 `getArticleById`，缓存等于白配。
  因此抽出 `ArticleCacheService` 承载缓存注解
- **`unless` 条件只缓存公开文章**：`status=1 && hidden!=1`。
  避免未发布正文常驻 Redis；这类文章访问低频，不缓存对性能无影响
- **浏览量不进缓存**：否则每次访问都要回写整个缓存对象，退化成「每请求一次 Redis 写」

### 2.3 一次自己引入又修复的回归

初版把归属判断写成 `vo.getAuthor().getId()`，原实现是 `article.getAuthorId()`。
差异：`selectDetailWithAuthor` 在**作者被逻辑删除时 `author` 为 null**，
会导致作者本人反而看不到自己的草稿/隐藏文章。
已改为在 restricted 分支查一次实体拿 authorId（草稿不走缓存、本就要查库，热路径不受影响）。

## 三、优化结果

### 3.1 数据对比

同一会话、同一套脚本、同一环境下测得（脚本严格校验业务码，非仅看 HTTP 状态）：

| 并发 | 优化前 QPS | 优化后 QPS | 提升 | 优化前 P95 | 优化后 P95 |
| --- | --- | --- | --- | --- | --- |
| 5 | 110.3 | 2855.6 | 25.9x | 61ms | 2ms |
| 10 | 220.8 | 4679.7 | 21.2x | 61ms | 3ms |
| 20 | 261.0 | **5730.0** | **21.9x** | 95ms | 5ms |
| 40 | 260.1 | 5520.9 | 21.2x | 185ms | 10ms |
| 80 | 264.3 | 5664.2 | **21.5x** | 343ms | **17ms** |
| 120 | 267.0 | 5365.6 | 20.1x | 520ms | 29ms |
| 200 | 272.0 | 5514.8 | 20.3x | 793ms | 42ms |

- **QPS 天花板：264 → 5730，约 21 倍**
- **P95 延迟（并发 80）：343ms → 17ms，约 20 倍**
- 优化前 QPS 在并发 20 后即饱和；优化后在 5–200 全区间稳定在 5300–5700

### 3.2 瓶颈转移（压测中采样）

| 组件 | 优化前 | 优化后 |
| --- | --- | --- |
| MySQL | 瓶颈所在 | **0.5% CPU，几乎空闲** |
| Redis | 低负载 | 66% CPU |
| 后端 | 等待数据库 | **430–450% CPU（成为新瓶颈）** |

瓶颈从数据库转移到应用 CPU，符合预期——数据库不再是无谓开销的来源。

### 3.3 功能正确性

优化未牺牲正确性，均已实测：

- 浏览量递增：212 → 213 → 214 ✓
- 数据库**不再被逐次写入**（访问 3 次后 DB 值保持不变）✓
- 定时回写落盘：Redis 7667 → 重启后 DB 7667，完全一致 ✓
- 不存在的文章仍返回业务 404 ✓
- 文章内容、作者关联正确 ✓
- 全程零失败请求 ✓

## 四、设计取舍与答疑

**问：为什么浏览量可以接受不精确？**
浏览量是弱一致数据，用户无感知。设计上接受「最多丢一个回写周期（5 分钟）的增量」，
换来的是吞吐提升一个数量级。若业务要求强一致，应改用 MQ 异步而非 Redis。

**问：Redis 挂了怎么办？**
计数 key 下次访问时会用数据库当前值重新初始化，降级为「从当前值继续计数」，
不会归零也不会崩溃，只是丢失未落盘的增量。

**问：为什么不直接用 MQ？**
本项目已重度依赖 Redis，不引入额外组件。且 MQ 方案每条访问都要发消息，
高 QPS 下消息量巨大，消费延迟也不可控。浏览量场景不需要 MQ 的可靠性保证。

**问：缓存和数据库一致性怎么保证？**
文章更新/删除/隐藏/取消隐藏四处均已有 `@CacheEvict`。
浏览量单独走 Redis，不进缓存，天然规避了「缓存里浏览量是旧值」的问题。

**问：怎么证明提升不是因为缓存预热？**
预热轮单独跑过：冷缓存约 1750 QPS，热缓存约 5700 QPS。
生产稳态是热缓存，故以 5700 为准；文档中也保留了冷启动数据。
